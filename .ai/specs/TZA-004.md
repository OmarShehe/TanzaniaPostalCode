# TZA-004: Compose Multiplatform address-picker UI module

## Summary
Add an optional `:ui` KMP module (Android, desktop JVM, iosArm64, iosSimulatorArm64) with two composables, `AddressSearchField` (debounced type-ahead) and `AddressPicker` (cascading Region → Kitongoji dropdowns), built on `AddressRepository` from `:core` only. Behaviour lives in two plain, unit-tested controller classes (`AddressSearchController`, `AddressPickerController`); the composables are thin views over their state, so most tests are fast coroutine tests and only a handful are Compose UI tests. The sample `:app` becomes a Compose screen showing both widgets on the real bundled DB. Key trade-offs: iOS is compile-only here (no Xcode), and Compose UI tests run on desktop JVM plus the connected Pixel.

## Module Impact
`:ui` (new), `:app` (Compose activity replaces the View sample), root `settings.gradle.kts`, `gradle/libs.versions.toml`, `.ai/context.md`. `:core` and `:data` unchanged. `:ui` depends only on `:core`; `:app` depends on `:ui`, `:data`.

## Architecture Conformance
- Layering: `:ui` -> `:core` only; no `:data`/SQL/`android.*` in `commonMain`; controllers depend on the `AddressRepository` interface.
- Logic vs view: cascade/debounce/validation rules only in controllers (unit-tested); composables hold no business rules.
- One top-level type per file; `explicitApi()`; public API = the two composables + `AddressPickerState` saveable helper; controllers/state internal.
- Id/text rules are not re-derived: `Level`, `AddressPath`, `AddressMatch` come from `:core`.
- Recorded in `.ai/context.md`: `:ui` package `com.omarshehe.tzaddress.ui`.

## Implementation Steps
1. Catalog + plugins + `include(":ui")`; skeleton `ui/build.gradle.kts` (targets android/jvm/ios, Compose deps) compiling for all targets (spike: compile for desktop, android, both iOS klibs).
2. Tests first for `AddressSearchController` (Red), then implement with `debounce`/`mapLatest`.
3. Tests first for `AddressPickerController`, then implement (levels, clearing, none-listed, requiredLevel, restore).
4. `AddressUiState` saver + tests.
5. Strings (en, sw) and the composables `AddressSearchField`, `LevelDropdown`, `AddressPicker`.
6. Compose UI tests (`runComposeUiTest`): search shows/select; cascade disabled/cleared; postcode shown; run on desktop JVM.
7. `:app`: Compose `MainActivity` with both widgets over `createAddressRepository`, close on destroy; replace theme/layout; assemble debug/release; install and drive on the Pixel; rotation check; Swahili check via `adb shell cmd locale`; screenshots to `docs/`.
8. Android device test for widgets (same tests) on the phone.
9. iOS klib compile for `:ui`; `.ai/context.md`; ticket scope notes; full verification (all modules' tests, `:app:assembleRelease`).

## Test Plan (TDD)
- `AddressSearchController` (virtual time): typing then <250 ms more keystrokes -> one search call with the last query; blank -> Idle and no call; results -> `Results` capped at 10; empty -> `NoMatches`; repository throws -> `Error` and later queries still work; a newer query cancels the older one (no stale results); `CancellationException` is not turned into `Error`.
- `AddressPickerController`: initial state (only Region enabled); choose region -> District enabled and populated; changing region clears district..kitongoji and emits; `requiredLevel = WARD` emits null until ward chosen then the ward path, then re-emits deeper; `requiredLevel = MTAA` with a ward that has no mtaa counts as complete ("None listed"); ward exposes 5-digit postcode; restore from `AddressPath` sets every level and loads options; unknown/failed repository -> error state, no crash.
- Saver: round-trips (level, id) and restores via `repository.path`; null when nothing selected.
- Compose UI: `AddressSearchField` shows suggestions with district, region, postcode; selecting fires `onSelected`; nonsense -> "No matches"; throwing repo -> inline error. `AddressPicker`: District disabled until Region chosen; postcode text appears; Swahili strings render with a Swahili locale (where the harness allows).
- Not unit-tested: pixel layout/spacing (checked on the phone + screenshots), iOS runtime.

## Risks & Gotchas
- **Compose plugins** must not leak to `:data`/`:core` (broke the plain-JVM compile in TZA-003); only `:ui`/`:app`.
- **Compose iOS unverified**: klib compile only; real iOS behaviour unknown.
- **Dropdown popups in UI tests** (ExposedDropdownMenu) can be finicky on desktop; the cascade rules are covered at controller level so UI tests stay minimal.
- **Swahili test** depends on locale switching in the test harness; if the desktop harness can't switch locales, verify Swahili on the phone and note it.
- **AGP-9 KMP + Compose resources + device tests** combo is new; first build may need tweaks.
- Existing screen reuse check: the only sibling screen is the TZA-003 View sample; its status/empty/error strings and "trail › separated" suggestion format carry over.
- The dataset has wards with no mtaa and mtaa with no kitongoji: both must render "None listed", not an empty dropdown.
