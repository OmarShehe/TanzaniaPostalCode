# TZA-002: Repeatable PDF importer with validation report

## Summary
Add a JVM-only `:importer` module with a Gradle task `importPostcodes` that reads `tzPostcodeList.pdf` and writes a canonical dataset (`dataset/tz-address.json`), a validation report (`dataset/import-report.md`) and an anomaly list (`dataset/import-anomalies.csv`). The parser works on word coordinates and derives column boundaries **from each page's own header row**, because the PDF's table columns shift on nearly every page. Key trade-off: the importer reproduces what the PDF prints (a 2012 snapshot, 30 regions); it does not patch in later administrative changes.

## What the research of the actual PDF found (verified, not assumed)
- 1,211 pages, US Letter, text layer present. PDF metadata: creation date **2012-07-30**, author "Maswala", no publisher/licence.
- **30 region banners** (`<NAME> REGION ‐ <code>`, non-ASCII hyphen U+2010), not 31. **Songwe is absent** (region created 2016) and Kigamboni district is absent, so the file predates them. The old repo lists had Songwe; this PDF does not.
- **Three table layouts**, each with a header row repeated on every page:
  - A (Dar es Salaam, 19 pages): `REGION POSTCODE WARD POSTCODE MTAA/VILLAGE KITONGOJI` — the "REGION" column holds the *district* (`ILALA CBD`, code `11`).
  - B (standard, 1,175 pages): `REGION POSTCODE DISTRICT POSTCODE WARD POSTCODE MTAA/VILLAGE KITONGOJI`.
  - Z (Zanzibar, pages 1196–1211, 16 pages): `REGION POSTCODE DISTRICT POSTCODE WARD (DELIVERY AREAS) POSTCODE SHEHIA` — no kitongoji level; a shehia is the mtaa-equivalent.
- **Column x-positions differ per page**: dozens of distinct header geometries (e.g. `MTAA/VILLAGE` at x=428…544). A fixed x-threshold cannot work. Data cells align to their header's left edge to within ~10 pt (e.g. WARD header 231 ↔ cell 231; POSTCODE header 359 ↔ cell 369).
- Page 215 has zero words (blank page). Header-less pages: 215 plus the 16 Zanzibar pages (their header uses `SHEHIA`, not `MTAA/VILLAGE`).
- Code rule holds across layouts: a ward postcode starts with its district code (Dar: `11101` under `11`; elsewhere `53101` under `531`). Dar district codes are 2 digits; others are 3.
- Mbozi (Mbeya region) is present as a district, consistent with a pre-Songwe snapshot.

## Architecture Conformance
No project architecture rules exist; following TZA-001's conventions: one top-level type per file, no logic in DTOs, `:core` is the only source of `AddressIds` and model types (importer never reimplements ID generation), importer depends on `:core` and never the reverse, `:importer` is never published. **New naming decision:** module `:importer`, package `com.omarshehe.tzaddress.importer`, output folder `dataset/`; recorded in `.ai/context.md` in this ticket's PR.

## Implementation Steps
1. Add catalog entries and plugin aliases; `include(":importer")`; create `importer/build.gradle.kts` (Kotlin JVM, toolchain 17, `implementation(project(":core"))`, PDFBox, serialization-json, kotlin-test) and the `importPostcodes` task (JavaExec on `ImportMainKt`, args from `-Ppdf`, `-PsourceEdition`, `-PgeneratedAt`, `-Pforce`, `-PoutDir` default `dataset/`; fails with a clear message if `-Ppdf` is missing).
2. `PageWords`/`Word`/`Line` types and `PdfWordExtractor` (PDFBox `PDFTextStripper` subclass capturing per-word x/y; lines grouped by y within 2 pt; words split on gaps larger than a space width; read PDF `CreationDate`).
3. `LayoutDetector`: find banner line via regex tolerant of hyphen variants (`‐ ‑ – - −`); find header line (contains `POSTCODE` and `MTAA/VILLAGE` or `SHEHIA`); classify A/B/Z by header word sequence; produce ordered column list with each header's xMin; column of a cell = last header with `xMin <= cell.xMin + 12`.
4. `RowParser`: for each non-header line, split words into columns; join adjacent words in one column (gap < 2× word height) into a cell; drop stray page-number/footer text (anomaly if unexplained).
5. `HierarchyBuilder`: state machine per layout. A: district column holds name+code; B: region col (name+code only on the region's first row; also carries the region name that must match the banner), district col; Z: same as B but "shehia" column produces mtaas with no kitongojis. Rules: a district cell starts a new district; a ward cell (name, 5-digit postcode) starts a new ward; a cell in the mtaa column starts a new mtaa; a cell in the kitongoji column appends to the current mtaa; continuation lines (blank left columns) belong to the current ward/mtaa; region taken from banner code. Emit anomalies for: postcode cell not matching the level's digit rule, a cell before any parent exists, a row with unrecognised column, possible wrapped name (single-column line with y-gap < 1.6 line heights and no postcode), duplicate name under one parent (informational, disambiguated by `AddressIds`).
6. `NameNormalizer`: trim, collapse whitespace, normalise quotes; title-case words except single letters (`A`, `B`), tokens with digits, and a small exception list (`na`, `wa`, `ya`, `la`, `cha`, `kwa` lower-case mid-name); preserve original text in the anomaly CSV only.
7. `DatasetModel` + `DatasetWriter`: sorted output (regions by code, districts by code, wards by postcode, mtaas and kitongojis in **source order**), `\n` line endings, stable formatting; `info.generatedAt` from `-PgeneratedAt` or now; `info.sourceEdition` from `-PsourceEdition` or the PDF creation date (`2012-07-30`); `info.version` = `"1"` bumped manually by the Maintainer.
8. `Validator`: checks and failure policy (see Acceptance Criteria); `-Pforce` still writes outputs but marks the report `FAILED`.
9. `ReportWriter`: `import-report.md` with dataset info, per-region and total counts, all validation results, absent-region note, first 50 anomalies; `import-anomalies.csv` (`page,line,kind,text`).
10. `ImportMain`: wire extractor → detector → parser → builder → validator → writers; exit code non-zero on policy failure.
11. Write `PdfFixtureBuilder` (test-only) generating small PDFs with words positioned at given x/y; then the tests.
12. Run the importer on `~/Downloads/tzPostcodeList.pdf`, review the report and anomalies, iterate on the parser until anomalies are under threshold and the independent counts match; commit outputs.
13. Update `.ai/context.md`; correct the ticket text (Scope notes).

## Test Plan (TDD)
Pure logic is tested on hand-built `PageWords` (no PDF); extraction is tested on generated PDFs.
- `LayoutDetector`: layout A/B/Z header sequences → correct kind and column x-boundaries; **two pages with different header x-positions map the same cell text to the same column**; blank page → `Blank`; banner with `‐` (U+2010), `-`, `–` → region name + code; header line not confused with a data row.
- `RowParser`: multi-word cell joins (`Kariakoo Magharibi`); cell 10 pt right of its header still lands in the header's column; two adjacent cells not merged across a column boundary.
- `HierarchyBuilder`: layout B happy path (region → district → ward → mtaas → kitongojis); layout A district-in-first-column with code `11`; layout Z shehia → mtaas with empty kitongojis; page-break continuation (mtaa/kitongoji rows with blank left columns after a repeated header); blank-left-column continuation after a ward; duplicate mtaa names (`Rubumba` twice) preserved in order and disambiguated via `AddressIds`; names with `"` and `'`; a kitongoji row before any mtaa → anomaly, not crash; ward postcode not 5 digits → anomaly `BAD_WARD_POSTCODE`.
- `NameNormalizer`: `KIVUKONI`→`Kivukoni`, `UPANGA MASHARIKI`→`Upanga Mashariki`, `Kigaga A` keeps `A`, `Mtambani "A"` keeps quotes, `Jang&apos;ombe` decoded `Jang'ombe`, whitespace collapse.
- `Validator`: duplicate ward postcode → failure naming the code; ward postcode prefix ≠ district code → failure; region count ≠ `expectedRegions` → failure; anomaly ratio above threshold → failure; clean data → pass; every failure message appears in the report.
- `DatasetWriter`: same model twice → byte-identical output; ordering rules (source order for mtaas/kitongojis).
- `PdfWordExtractor`: generated one-page PDF with positioned words → words with x within 0.5 pt of the drawn position, lines grouped correctly.
- **Real-PDF checks (opt-in, skipped with a visible message unless `-Ppdf`/`TZ_PDF` is provided; the PDF is not in the repo):** per-region ward counts equal an independent count from `pdftotext -layout` (ward 5-digit tokens in the ward column) and byte-identical output across two runs. These are the AC-3/AC-4 evidence for the maintainer machine.
- Not unit-tested: Gradle task wiring (verified by running the task), report prose.

## Risks & Gotchas
- **Edition is 2012.** Later changes (Songwe region, Kigamboni, newer districts/wards) are absent. Not fixed here; see checkpoint question.
- **Wrapped names.** A long ward/mtaa name that wraps onto a second line is indistinguishable from a continuation row without heuristics; flagged as `POSSIBLE_WRAPPED_NAME` for manual review, not silently merged.
- **Zanzibar postcodes:** the ward-level postcode sits in the ward column and shehia are child rows; treated as Ward → Mtaa. Shehia therefore appear as `Mtaa` in the model (documented in the ticket).
- **Region name/banner mismatch** (banner `DAR ES SALAAM` vs first-column text) is normalised, not compared literally.
- **Two data-quality traps already visible:** mixed case (wards upper-case in Dar/others, title-case elsewhere) and HTML entities in extracted text (`Jang&apos;ombe` appeared in the bbox export).
- PDFBox text-position API details differ between 2.x and 3.x; verified during implementation, not assumed.
- Performance: 1,211 pages; the task must finish in a reasonable time on a laptop (target under 2 minutes); reported in the PR.
- `pdftotext` is not a build requirement; the independent-count check is skipped when it's absent.
- **TZA-003 wording check:** it assumes one `district.code` PK across all regions; the importer's validator additionally fails on duplicate district codes across regions.
